### **I. Overview and Scope**

**1.1 Objective** This document provides a detailed description of the testing methodology and implementation used to verify compliance with the Functional Package for Transport Layer Security (TLS). The objective is to demonstrate that the Target of Evaluation (TOE) satisfies the specific security functional requirements (SFRs) defined in the package.

[https://www.niap-ccevs.org/static\_html/protection-profile/519/PKG\_TLS\_V2.1.html](https://www.niap-ccevs.org/static_html/protection-profile/519/PKG_TLS_V2.1.html)

**1.2 Target of Evaluation (TOE)** The Target of Evaluation (TOE) for this testing is an Android mobile device.

**1.3 Compliance Claim and Evaluation Target Scope** Given that the TOE is an Android device, the evaluation focuses specifically on verifying the FCS\_TLSC\_EXT (TLS Client) Security Functional Requirements (SFRs). The scope of this evaluation encompasses standard internet clients operating within the Android environment, with a specific focus on APIs such as HttpURLConnection and OkHttp3.

The following table summarizes the compliance requirements and the specific evaluation target scope for each protocol and role:

| Protocol | Role | Requirement ID | Evaluation Target Scope |
| :---- | :---- | :---- | :---- |
| **TLS** | Client | **FCS\_TLSC\_EXT** | Standard internet clients (e.g., Chrome/OkHttp3). Targets HttpURLConnection, OkHttp3 APIs. |
| **DTLS** | Client | **FCS\_DTLSC\_EXT** | Streaming and real-time communication clients (e.g., Google Meet). |
| **TLS** | Server | **FCS\_TLSS\_EXT** | Server-side implementations (Not applicable for most Android TOEs). |
| **DTLS** | Server | **FCS\_DTLSS\_EXT** | Server-side streaming implementations. |

**Note:** While DTLS Client testing (`FCS_DTLSC_EXT`) is technically possible, it presents slightly higher testing difficulty and is considered secondary to the primary focus of verifying `FCS_TLSC_EXT` compliance.

### **II. Test Methodology**

**2.1 Test Environment and Infrastructure** 

To ensure strict test repeatability and minimize external environmental dependencies, the testing methodology utilizes a hybrid approach combining public baselines with a self-contained, easily reproducible local test environment:

* **Standard Validation:** The widely recognized `badssl.com` (a Chromium sub-project) is utilized to verify standard TLS connection states, including basic legacy protocol rejection and expired/invalid certificate handling.  
* **Custom Security Validation (Reproducible Local Server):** To rigorously test specific negative scenarios mandated by the PP (e.g., Downgrade Protection, forced Null Ciphers, and active rejection of unsupported parameters during the handshake), a custom, locally hosted test server environment is employed. This environment is packaged for easy reproduction by evaluators (e.g., utilizing lightweight Python scripts or OpenSSL `s_server` configurations).  
* **Certificate Management:** To facilitate local testing without triggering spurious validation errors that would obscure the test results, a dedicated **Custom Test Root CA** is generated. This Root CA certificate is installed into the TOE's trust store. This ensures the TOE successfully performs Reference Identifier and Certificate Path validation (as per **FCS\_TLSC\_EXT.1.5**), allowing the tests to accurately focus on protocol-level negotiations and cryptographic boundary enforcement.

**2.2 Verification Method** The primary verification mechanism relies on dynamic network packet analysis. Network traffic during the TLS handshake is captured using `tcpdump`. To handle the specific Android SLL2 (Linux Cooked Capture v2) packet format generated by the TOE, a modified `io.pkts.pcap` library is employed to accurately parse the PCAP files and inspect the TLS records (e.g., verifying extensions like SCSV or SessionTickets).

**2.3 Test Automation Tools** Test cases are implemented as JUnit tests and executed within the Android environment using the `testbed-core` framework. These automated tests trigger the network connections to the respective test servers and subsequently execute the PCAP analysis to ensure the TOE's behavior strictly aligns with the cryptographic boundaries defined in `FCS_TLSC_EXT`.

### **III. Detailed Test Case Mapping**

This section maps the specific Security Functional Requirements (SFRs) defined in `FCS_TLSC_EXT` to the corresponding test cases. To clearly define the evaluation progress and methodology, the testing is divided into two phases: currently implemented baseline tests and planned active security verification tests.

#### **3.1 Phase 1: Currently Implemented Baseline Tests (Using badssl.com)**

The following test cases are **currently implemented** using the public `badssl.com` infrastructure. These tests verify the TOE's passive behavior when connecting to endpoints with strictly configured constraints.

* **FCS\_TLSC\_EXT.1.1 & 1.2 (Protocol Versions \- Passive Refusal):**  
  * `testNormalHost`: Confirms successful connection using TLS 1.2 or TLS 1.3.  
  * `testTls10Reject` / `testTls11Reject`: Verifies that connection attempts fail when the target server *only* supports legacy protocols (TLS 1.0/1.1).  
* **FCS\_TLSC\_EXT.1.3 & 1.4 (Cryptographic Ciphers \- Passive Refusal):**  
  * `testRc4Reject` / `test3DesReject` / `testNullCipherReject`: Verifies connection failure when the target server *only* supports prohibited weak or null ciphers.  
* **FCS\_TLSC\_EXT.1.5 & 1.6 (Certificate Validation):**  
  * `testExpiredHost` / `testInvalidHost`: Confirms connection termination with an appropriate exception (`SSLHandshakeException` or `CertificateException`) when presented with expired certificates or a mismatched Reference Identifier.  
* **FCS\_TLSC\_EXT.2, EXT.5, EXT.6 (Handshake Extensions \- Passive PCAP Analysis):**  
  * Verified continuously within the `analyzePcap` routine during successful connections.  
  * Confirms the presence of SCSV (0x00FF) or `renegotiation_info` (0xFF01) for renegotiation protection.  
  * Confirms the presence of `SessionTicket` (0x0023) and `key_share` / `psk_key_exchange_modes` for resumption.  
  * Confirms the **absence** of `early_data` (0x002A) to verify 0-RTT is disabled.

#### **3.2 Phase 2: Additional Active Verification Requirements (Custom Test Server)**	

To fully satisfy the `FCS_TLSC_EXT` requirements, the following tests require a locally hosted custom server to actively simulate malicious server behavior. This phase is categorized into mandatory requirements and conditional/optional verifications.

**\[Mandatory Verifications\]** These tests are strictly required for compliance.

* **FCS\_TLSC\_EXT.1.1 (Active Rejection of Legacy Protocols):**  
  * **Requirement Focus:** The TOE must actively terminate the connection if a server attempts to negotiate a prohibited legacy protocol version.  
  * **Test Implementation:** The custom local server will respond to a valid `ClientHello` by explicitly forcing a `ServerHello` with SSLv3, TLS 1.0, or TLS 1.1.  
  * **Expected Evidence:** PCAP analysis must show the TOE sending a fatal alert (e.g., `protocol_version`) and immediately terminating the handshake.  
* **FCS\_TLSC\_EXT.4 (Secure Renegotiation \- Active Verification):**  
  * **Requirement Focus:** The TOE must actively reject insecure renegotiation attempts initiated by the server.  
  * **Test Implementation:** After a successful initial handshake, the custom server will initiate an insecure renegotiation request (omitting the `renegotiation_info` extension).  
  * **Expected Evidence:** PCAP analysis must show the TOE rejecting the renegotiation attempt with a fatal alert (e.g., `no_renegotiation`).

**\[Conditional / Optional Verifications\]** The following test is included if the TOE explicitly claims protocol fallback capabilities.

* **FCS\_TLSC\_EXT.3.1 (Downgrade Protection):**  
  * **Requirement Focus:** The TOE must implement mechanisms to prevent downgrade attacks. *Note: This requirement is conditional. It is not strictly mandatory unless the Security Target (ST) explicitly claims that the TOE implements a protocol fallback mechanism.*  
  * **Test Implementation:** The custom server will simulate a network anomaly causing the client to retry, and intentionally attempt to force a downgrade to a lower protocol version.  
  * **Expected Evidence:** PCAP analysis must demonstrate that the TOE detects the downgrade attempt (e.g., via the use of `TLS_FALLBACK_SCSV`) and safely terminates the handshake.

### **IV. Identified Concerns and Limitations**

While the current Phase 1 testing methodology (utilizing `badssl.com`) effectively demonstrates the TOE’s baseline compliance with standard TLS constraints, there are several identified limitations in the current test architecture. These limitations primarily stem from the inability of standard public test servers to actively simulate malicious or state-manipulating handshake behaviors required to fully satisfy the mandatory Security Functional Requirements (SFRs).

#### **4.1 High Priority: Incomplete Verification of Secure Renegotiation (FCS\_TLSC\_EXT.4)**

* **Concern:** Current testing merely performs passive static analysis on the initial `ClientHello` packet to verify the presence of renegotiation support signals (e.g., SCSV 0x00FF or the `renegotiation_info` extension). It does not verify the TOE's actual operational behavior when a renegotiation is actively requested by the server *after* the initial handshake is established.  
* **Evaluation Impact:** Because `FCS_TLSC_EXT.4` is a strictly mandatory requirement, evaluating only the initial signaling is insufficient. To provide complete evaluation evidence (ATE\_COV), a custom test server is required to intentionally trigger an insecure or secure renegotiation request post-handshake, definitively proving that the TOE either handles it securely or actively rejects the attempt with a fatal alert.

#### **4.2 High Priority: Lack of Active Rejection Verification (FCS\_TLSC\_EXT.1)**

* **Concern:** The existing negative test cases (e.g., `testTls10Reject`, `testNullCipherReject`) only verify that the TOE refuses to connect to a server configured *exclusively* with weak parameters. They do not verify the TOE's active defense mechanisms against illegal selections during a standard negotiation.  
* **Evaluation Impact:** Strict adherence to mandatory requirements `FCS_TLSC_EXT.1.1` and `FCS_TLSC_EXT.1.3` requires demonstrating that if the TOE sends a valid `ClientHello`, and a malicious server explicitly responds with a `ServerHello` forcing an unproposed Null Cipher or a prohibited legacy protocol, the TOE will actively terminate the handshake. The current reliance on standard public servers prevents the execution of these specific, protocol-violating `ServerHello` injections.

#### **4.3 Medium Priority: Limitation in Verifying Downgrade Protection (FCS\_TLSC\_EXT.3.1)**

* **Concern:** The current passive test infrastructure cannot simulate the complex network anomalies or active Man-in-the-Middle (MitM) interventions required to trigger a protocol downgrade attempt.  
* **Evaluation Impact:** While `FCS_TLSC_EXT.3.1` is a conditional requirement (mandatory only if the TOE claims a fallback mechanism), completely verifying it requires an external, maliciously configured test server to force the TOE into a fallback state. Currently, it is impossible to capture the PCAP evidence proving the TOE's correct validation of the TLS 1.3 downgrade signal within the Server Random or its generation of the `TLS_FALLBACK_SCSV` signal.

**4.4 Implementation Note: PCAP Parsing Fragility (Android SLL2)**

* **Concern:** The Android OS utilizes the Linux Cooked Capture v2 (SLL2) link-layer header format when performing packet captures across network interfaces. The current test automation framework relies on the `io.pkts.pcap` library, which does not natively support the SLL2 format.  
* **Evaluation Impact:** To bypass this limitation, "monkey patches" (runtime code modifications) have been temporarily implemented to force the parser to interpret the SLL2 traffic. From a Common Criteria perspective, test tools must be robust and the results strictly reproducible by an independent evaluator. The current patching mechanism poses a risk to the long-term maintainability and independent repeatability of the PCAP analysis phase.

### **V. Next Steps and Resource Availability**

To address the limitations identified in Phase 1 and to facilitate independent verification by evaluators, the following logistical and resource plans are established:

#### **5.1 Phase 2 Implementation Strategy (Pending Consultation)** 

The architectural and operational deployment strategy for the custom test server (required for Phase 2 active verifications, such as `FCS_TLSC_EXT.1` and `FCS_TLSC_EXT.4`) is currently under review. Further consultation is required to determine the optimal balance between strict test isolation (e.g., local execution) and ease of deployment.

#### **5.2 Tooling and Cross-Platform Distribution** 

The automated test suites are executed using the `testbed-core` framework. To ensure seamless and independent execution by evaluators, the test tools can be compiled and distributed as standalone executables for Windows, Linux, and macOS environments. These binaries require no external runtime environments (e.g., no JRE installation is necessary on the host machine). Upon request, a fully configured test package, complete with the necessary execution parameters, can be provided.
